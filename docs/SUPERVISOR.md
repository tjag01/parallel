# Supervising parallel lanes

Parallel came out of a solo project that ran four Claude Code lanes all day, and often overnight. One person owned
the decisions. A second Claude acted as designer and reviewer: it wrote each lane's task file, read each report, and
ruled on every stop. Below is the method that made that safe and fast. None of it is enforced by the tool; it is a
discipline you put into your task files.

## 1. Every task is a file, and every file is read whole

A lane works from one Markdown file (a *sprint*) that states:

- **Goal and scope:** what changes, roughly how big, and which files it may touch. Name the files it may **not**
  touch too.
- **What is already known,** with `file:line` for every fact the plan rests on. A fact you cannot cite is a belief,
  and beliefs go into the checks below, not into the plan.
- **The decisions already made** (the "register"), each with its reason.
- **Verified assumptions,** run first. These are greps and tests the agent runs *before* writing any code, each with
  an explicit stop condition: "if this returns X, STOP and report".
- **Steps,** each ending in a commit and a push, with the exact commands.
- **Exit criteria:** the tests and checks that must be green, the report's shape, and "do not suggest next tasks".

`examples/sprint-template.md` is a starting point.

## 2. Halt and report beats improvising

Tell every lane that any contradiction, unexpected result, ambiguity or surprise is a **STOP**. It reports what it
found, with its evidence and its own lean, and waits. In practice the agent's improvisation past a stop was the wrong
call nearly every time. The stops themselves were usually the most valuable output of the day: most real bugs
arrived as a lane saying "this premise in your file is false".

Two habits make stops cheap:

- **Predictions first.** The agent writes down what it expects each check to show *before* running it, then marks
  each prediction confirmed or refuted. A refuted prediction tells you exactly which belief was wrong.
- **Red first.** Every new test is shown failing on the old code before it passes on the new.

## 3. Rulings are files too

When a lane stops, the supervisor reads the report (deviations first, green checkmarks last) and writes a short
**ruling** file: which option, why, and any added condition. Then:

```
cc-parallel send B B-ruling-step0.md
```

The relay types "Read …/B-ruling-step0.md whole (sha256 starts …) and follow it." into lane B. The sha256 means the
lane can confirm it read the version you meant. Pre-rule what you can, for example "if the measurement shows X, take
option 1; if Y, stop again". That way one ruling covers the likely outcomes and saves a round trip.

## 4. Keep the lanes apart

- One worktree per lane. Lanes push to the shared branch with a rebase, and **a merge conflict is a STOP.** The
  exception is a conflict where no line was changed by both sides, proven by a script that asserts it.
- Generated files (codegen, lockfiles) are regenerated by their one writer, never merged by hand.
- Name the other running lanes in each task file, with what they touch. Most conflicts are predictable.

## 5. Read what the lanes cannot say on one screen

- The relay keeps `panes/<lane>.txt`, the last 200 lines of each lane. A long stop message can still scroll past
  that, so give your tasks a standing instruction: "write any STOP to `<scratch>/STOP_QUESTIONS.md` as well as to the
  screen". The supervisor then reads the file, not the scrollback.
- Ghost text in a lane's input box is often Claude Code's own suggestion, not something a person typed. The relay
  clears the input line before it types.
- Use `ON_CHANGE` or `cc-parallel status` so an idle lane is noticed in seconds, not at the next scheduled look.

## 6. Hard limits belong in every kickoff

If you run lanes unattended, the kickoff templates are where you put the rules that must hold whatever the task
says. Examples from the original project:

- never delete files (move them aside instead);
- never touch the development database, and never plug a hardware key in;
- stop processes by PID, never by name;
- nothing under `/tmp`, so scratch stays inside the worktree;
- only the named models;
- no network beyond the package registries.

## 7. Size tasks small

A 120-line change took about 17 minutes and came back sharper than a 700-line one that took 40. Split a task when it
holds two design problems, or when one half is mechanical and the other needs judgement. A queue of small tasks
across four to eight lanes beats a few large ones.
